The Janus monolith (monastero-janus-backend / -frontend) stays untouched — code, not data. New widgets ship as independent deployables that read the shared schema and verify monolith-issued JWTs. These candidates ask one question: where is the seam that lets a new widget strangle the monolith without anyone editing the monolith?

The gateway is the strangling seam. Migrate a route monolith→service by re-pointing one entry.

Decision (see ADR-0002)

  • ✦ a dumb reverse proxy (Caddy), not a BFF — no business logic
  • ✦ its own top-level deployable, outside both monolith repos
  • ✦ single front door, uniform same-origin across local/staging/prod
  • ✦ longest-prefix routing; unknown prefixes catch-all → monolith
  • ✦ one fresh prefix per widget; no reuse of a monolith prefix
  • ✦ services become non-browser-facing → drop CORS entirely
  • ✦ realtime (WS/SSE) rides through the gateway, JWT-verified by each service — not Supabase direct
  • ✦ gateway terminates TLS in staging/prod

Corrections to the original framing

  • ✦ the "Before" leak was hypothetical — the service is referenced nowhere in the frontend; the gateway prevents the leak, it doesn't clean one up
  • ✦ G3's fix ("tighten the service's CORS to the gateway's origin") was wrong — CORS doesn't govern server-to-server calls; services drop CORS instead
  • ✦ "Widget Gateway" was a misnomer — it fronts the frontend, the whole monolith, and TLS; renamed edge-gateway

Problem

Every new widget service copies DataResponse, verify_access_token, require_scopes and the search_path session — shallow duplication with no locality for the JWT contract.

Solution

A deep praim-widget-kit package: one import yields the response contract, the auth dependency, and the DB session seam.

Wins

  • ✦ locality: JWT & scope logic in one module
  • ✦ leverage: one import, N services
  • ✦ interface shrinks; implementation absorbs the plumbing
  • ✦ next widget starts thin
  • ✦ the kit is the test surface for auth
Touches ADR-0001 — but compatible. The ADR says DataResponse is copied, not imported to avoid depending on the monolith. The kit is a third package both new services depend on — not the monolith — so the ADR's intent holds. It does revisit the copy-paste choice across the new services; worth a one-line ADR amendment.

Give ADR-0001's "schema is a contract" an actual seam

A monolith column rename breaks the route with no compile-time signal — exactly ADR-0001's warning, with nowhere to localize it.

After — one module embodies the schema contract

HTTP route /raw
DemographicRepo fetch_territory(name) → row sole owner of table/column/search_path knowledge
build_demographic_response()

The repo interface is the schema contract — and the home for the missing integration / contract test.

Problem

ADR-0001 says "treat the shared schema as a contract," but the contract has no module — raw SQL with table/column names sits inline in the route handlers.

Solution

A DemographicRepo module: the single place that knows the table, columns and search_path, returning domain rows.

Wins

  • ✦ locality: schema knowledge in one module
  • ✦ a seam for the missing contract test
  • ✦ handlers stop knowing columns
  • ✦ two adapters: real Postgres + in-memory fake

Sizing: only two queries today, so the deletion test is weak now — but the coupling risk is real and grows with the anticipated territory_name → regions join.

Gaps & risks · would-block-or-bite

What's missing before any of this runs

These are not deepening candidates — they are concrete operational / correctness gaps found while reading the code. The candidates above make the architecture better; these decide whether it works at all.

Blocker runtime fails without it Warning works, but bites later Cleanup dead weight
Blocker

Runtime configuration is absent

demographic-service: config/__init__.py:21-23 (empty defaults) · docker-compose.dev.yml (no env_file / environment) · no .env, no .env.example

Settings defaults database_url and jwt_verification_key to empty strings, and the dev compose passes neither an env_file nor an environment block. The service boots and /health answers (the engine is lazy), but every real call fails — no DB connection, no verifiable JWT.

Fix: add a .env.example (DATABASE_URL, JWT_VERIFICATION_KEY, JWT_ALGORITHM) and wire an env_file into the compose service. This is the most likely thing standing between you and a working call.

Blocker

The service is not wired into the frontend

frontend/src — no reference to /demographics or :28001 in any dashboard config

Nothing in the frontend points at the demographic service. resolveUrl (fetch-wrapper.ts:10) only reaches an external widget if a dashboard config carries an absolute URL — and none do yet. Until the edge gateway (ADR-0002) exists (or a stop-gap absolute URL is added), the widget is unreachable from the UI. The "Strangler Fig" is, for now, theoretical.

Fix (ADR-0002): resolved by the edge gateway — point NEXT_PUBLIC_BACKEND_URL at the gateway (same origin) and use relative paths only.

Warning

CORS is wide open

demographic-service: app.py:15-21

allow_origin_regex=r"https?://.*" with allow_credentials=True accepts any origin. It works (Starlette reflects the matched origin), but it is "allow everything."

Fix (ADR-0002): with the same-origin edge gateway, the browser never calls this service directly — the gateway does, server-to-server, where browser CORS does not apply. The service drops CORS entirely, rather than "tightening it to the gateway's origin" (a meaningless target: the gateway is not a browser and sends no enforced Origin).

Warning

Schema coupling has no safety net

demographic-service: demographics_router.py:108-141 (inline SQL) · docs/adr/0001-shared-database.md

Exactly ADR-0001's warning: a monolith column rename breaks the read query with no compile-time signal, and there is no integration / contract test today. The coupling is real and grows with the anticipated territory_name → regions join.

Fix: this is what candidate 3 (DemographicRepo) addresses — a single module that owns the schema knowledge and hosts the missing test.

Warning

The monolith is vendored as plain directories

monastero-janus-backend/ · monastero-janus-frontend/ — no .gitmodules, no nested .git

The "read-only base" lives as ordinary committed folders, not submodules. It works, but it bloats the repo, mixes histories, and pins no monolith version that the microservice is tested against — yet the whole design depends on the monolith's schema and JWT contract.

Fix: if the monolith is meant to be an immutable external dependency, prefer git submodules (or a separate repo + version pin); if it is only local reference material, consider not committing it.

Cleanup

Dead /ping endpoint

A leftover placeholder from "Task 03," already superseded by /raw and /territories. Dead weight behind the auth guard.

Fix: delete it.

Top recommendation

Start with the edge gateway → candidate 1 · resolved (ADR-0002)

Without it, "Strangler Fig" is just two services the frontend already knows about individually, with routing smeared across dashboard config. The gateway is the pattern's defining seam: it lets new widgets strangle the monolith one route at a time, keeps the frontend's single-origin assumption intact, and never edits the monolith. Build it first — then candidate 2 (the Widget Service Kit) makes every service behind the gateway thin.
