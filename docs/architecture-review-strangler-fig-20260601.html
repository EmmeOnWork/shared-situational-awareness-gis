The Janus monolith (monastero-janus-backend / -frontend) stays untouched — code, not data. New widgets ship as independent deployables that read the shared schema and verify monolith-issued JWTs. These candidates ask one question: where is the seam that lets a new widget strangle the monolith without anyone editing the monolith?

The gateway is the strangling seam. Migrate a route monolith→service by re-pointing one entry.

Decision (see ADR-0002)

  • ✦ a dumb reverse proxy (Caddy), not a BFF — no business logic
  • ✦ its own top-level deployable, outside both monolith repos
  • ✦ single front door, uniform same-origin across local/staging/prod
  • ✦ longest-prefix routing; unknown prefixes catch-all → monolith
  • ✦ one fresh prefix per widget; no reuse of a monolith prefix
  • ✦ services become non-browser-facing → drop CORS entirely
  • ✦ realtime (WS/SSE) rides through the gateway, JWT-verified by each service — not Supabase direct
  • ✦ gateway terminates TLS in staging/prod

Corrections to the original framing

  • ✦ the "Before" leak was hypothetical — the service is referenced nowhere in the frontend; the gateway prevents the leak, it doesn't clean one up
  • ✦ G3's fix ("tighten the service's CORS to the gateway's origin") was wrong — CORS doesn't govern server-to-server calls; services drop CORS instead
  • ✦ "Widget Gateway" was a misnomer — it fronts the frontend, the whole monolith, and TLS; renamed edge-gateway

Collapse the copied contract into a Widget Service Kit

demographic-service: models/pyd_models.py:6 · security/jwt_utils.py:17 · security/auth_dependencies.py:74 · config/pgsql_config.py:41

Reviewed in a grilling session (2026-06-03). Outcome: defer the extraction until a second service actually exists. With only demographic-service in tree, this is a deduplication at N=1 — every win below (one import, N services, a thin next widget) is worth zero until there is a second consumer. Extracting a shared shape from a single example also risks freezing demographic-specific plumbing as if it were universal. The boxes below are kept as the original framing; the corrected reading is in the conclusion box.

Interface shrinks to one import; implementation absorbs RSA, scope-parsing, pool config.

Problem

Every new widget service copies DataResponse, verify_access_token, require_scopes and the search_path session — shallow duplication with no locality for the JWT contract.

Solution

A deep praim-widget-kit package: one import yields the response contract, the auth dependency, and the DB session seam.

Wins

  • ✦ locality: JWT & scope logic in one module
  • ✦ leverage: one import, N services
  • ✦ interface shrinks; implementation absorbs the plumbing
  • ✦ next widget starts thin
  • ✦ the kit is the test surface for auth

Conclusion (grilling 2026-06-03): deferred, not dropped. The idea is sound but premature. Record the intent — "at the second service, extract the pieces that prove identical to the copy" — and leave the copies until then.

  • N=1 means no leverage yet. "One import, N services" and "next widget starts thin" pay off at the second copy, not the first.
  • The four pieces are not equal extraction candidates. DataResponse (a 10-line DTO) is the safest; the auth pair (verify_access_token + require_scopes) is the real deep value; get_session_context is already a demographic-specific shape ("read the shared DB with search_path=public") — a compute-only or own-table widget would not use it. The second service is what reveals which are truly common.
  • The kit does not fix drift against the monolith. The monolith is the source of truth for the JWT claims and the DataResponse shape, and ADR-0001 forbids importing it. A kit unifies the widget siblings; it still drifts from the monolith exactly as the copies do.
  • ADR at extraction time, not now. Introducing a shared dependency across services is a genuine reversal of ADR-0001's "copied, not imported" and a new deployment-coupling point — worth its own ADR when the second service forces it, not a speculative one-liner today.

Give ADR-0001's "schema is a contract" an actual seam

Before — handlers know column names

HTTP route /raw
SELECT * FROM demographic WHERE…
knows table + columns + search_path
build_demographic_response()

A monolith column rename breaks the route with no compile-time signal — exactly ADR-0001's warning, with nowhere to localize it.

After — one module embodies the schema contract

HTTP route /raw
DemographicRepo fetch_territory(name) → row sole owner of table/column/search_path knowledge
build_demographic_response()

The repo interface is the schema contract — and the home for the missing integration / contract test.

Problem

ADR-0001 says "treat the shared schema as a contract," but the contract has no module — raw SQL with table/column names sits inline in the route handlers.

Solution

A DemographicRepo module: the single place that knows the table, columns and search_path, returning domain rows.

Wins

  • ✦ locality: schema knowledge in one module
  • ✦ a seam for the missing contract test
  • ✦ handlers stop knowing columns
  • ✦ two adapters: real Postgres + in-memory fake

Sizing: only two queries today, so the deletion test is weak now — but the coupling risk is real and grows with the anticipated territory_name → regions join.

Warning · the one open decision

The monolith is vendored as plain directories

monastero-janus-backend/ · monastero-janus-frontend/ — no .gitmodules, no nested .git

The "read-only base" lives as ordinary committed folders, not submodules. It works, but it bloats the repo, mixes histories, and pins no monolith version that the microservice is tested against — yet the whole design depends on the monolith's schema and JWT contract. This is the same unpinned contract the deferred kit (candidate 2) could not import anyway.

Fix (genuine decision — hard to reverse, unresolved as of 2026-06-03): if the monolith is meant to be an immutable external dependency, prefer git submodules (or a separate repo + version pin); if it is only local reference material, consider not committing it. This is the only gap here that warrants its own grilling/ADR rather than execution.

demographics_router.py:158-165 · test_auth.py:3 (PROTECTED) · docker-compose.yml:46-48 (reachability smoke)

The original "delete it" was wrong. /ping is the only DB-free endpoint behind the auth guard, and two things now lean on exactly that: the whole auth suite targets it (PROTECTED = "/demographics/ping"), and the gateway commit made it the documented reachability smoke (a demographics:read token returns 200 through the gateway without seeding the DB). /raw and /territories both hit the DB, so they cannot stand in. Top recommendation

Start with the edge gateway → candidate 1 · resolved (ADR-0002)

Without it, "Strangler Fig" is just two services the frontend already knows about individually, with routing smeared across dashboard config. The gateway is the pattern's defining seam: it lets new widgets strangle the monolith one route at a time, keeps the frontend's single-origin assumption intact, and never edits the monolith. Build it first — then, once a second service actually exists, candidate 2 (the Widget Service Kit) makes every service behind the gateway thin. Deferred at N=1 (grilling 2026-06-03): with only demographic-service in tree the kit has no second consumer to be thin.
